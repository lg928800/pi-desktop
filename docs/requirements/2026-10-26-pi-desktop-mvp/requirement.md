# pi-desktop MVP — 需求与设计草案

- 状态：**设计待拍板**（2026-10-26）

- 关联：`../../HANDOFF.md`

## 1. 背景

pi 是终端 agent，日常使用中三个体验瓶颈：

1. 长会话/长 diff 在终端里难以回看；
2. 多个任务并行时只能开多个终端窗口，状态（跑着/等审批/出错）不可见；
3. 危险操作只能"看着它跑"，事后无审批记录。

市面上同类桌面端（Conductor / Vibe Kanban / Crystal / Cursor）已验证「任务 ↔ 工作目录 ↔ 会话」三元绑定的形态成立。

## 2. 目标 / 非目标

**目标**
- 把一次 agent 任务完整可视化：流式消息、工具调用、文件改动、审批、结束状态。
- 支持多会话并行，且单个会话崩溃不影响其他。
- 危险操作在 UI 层可控、可审计。

**非目标（本期明确不做）**
- 自建 agent 引擎或模型接入层（pi 已解决）
- 云端同步、多用户、账号体系
- 插件市场、移动端
- 编辑器的完整实现（diff 只做展示/审批，不做编辑）

## 3. 架构

```
UI (React + TS + Vite)
  │  WebSocket  127.0.0.1 + 一次性 token
Bridge (Node sidecar)  ← 唯一后端
  │  stdin/stdout JSONL
pi 子进程 × N        （每个会话一个 `pi --mode rpc`）
```

要点：
- **一个会话一个子进程**：pi 的 RPC 是单会话模型（`switch_session` 只能顺序切），并行必须多进程；崩溃隔离是附带收益。
- **无数据库**：会话列表/内容来自 `~/.pi/agent/sessions/**.jsonl`（契约见 pi 的 `session-format.md`），运行态走 RPC。
- **外壳后置**：Bridge 是独立 Node 进程、UI 是纯 Web，因此 Tauri/Electron 套壳只改启动方式，不影响业务代码。

## 4. 技术选型

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 集成方式 | `pi --mode rpc` 子进程 | 官方为自定义 UI 设计的通道；语言无关；进程隔离 |
| 是否 fork pi | **否** | TUI 是 ANSI 渲染，改 Web 等于重写；fork 要无限期 rebase；换品牌官方给了 `piConfig` |
| MVP 外壳 | 本地 Web（待拍板） | 迭代最快，不让打包链拖慢打磨 |
| 二期外壳 | Tauri 2 优先，Electron 备选 | 体积/内存；Tauri 需 Rust 工具链 |
| 语言 | TypeScript 全栈 | 与 pi 同生态，`RpcClient` 可直接复用思路 |

## 5. 五个技术难点（实现前必须定方案）

1. **流式渲染**：`message_update` 的 `text_delta` 增量拼接显示，`message_end` 到达时用权威消息整体替换；结束判定用 `agent_settled`。
2. **帧解析**：字节流按 `\n` 切；禁用 `readline`（会误切 `U+2028`/`U+2029`）。
3. **审批流**：`extension_ui_request` 的 `confirm`/`select` → 非阻塞弹窗队列 + 倒计时（协议自带 `timeout`，超时 agent 自行 resolve）。
4. **长会话性能**：单会话可达数 MB / 上千条消息（实测最大 9.3MB）→ 虚拟滚动 + 旧消息折叠。
5. **进程生命周期**：UI 断线/刷新不杀 agent；重连后通过 `get_messages` + `get_state` 重建现场，不依赖前端缓存。

## 7. 参考案例与可复用模式

| 产品 | 可拿的模式 |
| --- | --- |
| Conductor | 任务 ↔ worktree ↔ 会话 三元绑定（最贴近本项目形态） |
| Vibe Kanban | 看板式任务状态机，比"聊天列表"更贴合"派活"心智 |
| Crystal | 多会话池 + 快速切换 |
| Cursor | 工具结果就地渲染（改文件 → 内联 diff），而非打印日志 |
| Zed agent panel | 信息密度与视觉克制的基线 |

四条结论：① 一次任务 = 一个会话 = 一个工作目录；② 工具调用是卡片不是日志行；③ 审批是一等公民；④ 状态五态分明（跑着/等审批/等模型/结束/出错）。

## 8. 安全底线

- WebSocket 仅绑 `127.0.0.1`，启动生成一次性 token；拒绝非本地来源。
- 审批默认开启且留痕。
- 密钥只在 pi 的 `auth.json`，Bridge/UI 不接触明文。
- 不提供隐藏的"全部自动批准"开关。
